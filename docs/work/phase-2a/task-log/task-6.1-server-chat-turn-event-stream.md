# Task 6.1 — Server chat turn: detached execution + session event stream

### Task
Give the Express server the chat turn: `POST /api/chat` starts a turn through the core engine and answers 202; the turn runs to completion and persists regardless of any client; observers follow it through one SSE stream per client over a per-user-day event log with a monotonic `seq` cursor; `POST /api/chat/cancel` is the only abort path.

Change map, in dependency order:
1. **Wire contract** — `packages/api/src/chat.ts`: `TurnKind`, `TurnOutcome`, `TurnErrorPhase`, `TOOL_NAMES`/`ToolName`, the seven `SessionEvent` types plus `ResyncEvent`; error codes `input_rejected`, `invalid_request`, `turn_failed`.
2. **Server model provider** — `apps/server/src/model-provider.ts`: pure factory `createModelProvider({ provider, modelId })`, per-provider defaults and API-key env names; `config.ts` reads `GTD_PROVIDER`/`GTD_MODEL` and verifies the key at boot.
3. **Event log** — `apps/server/src/chat/event-log.ts`: append-only, epoch-seeded `seq`, synchronous fan-out, `since(cursor)` with `"resync"`.
4. **Sink adapter** — `apps/server/src/chat/turn-events.ts`: `TurnSink` → events; tool-row derivation (`target`, `summary`); `turnEnd` → `error` + `turn-end`, then release.
5. **Registry** — `apps/server/src/chat/turn-registry.ts`: per user the session cache, one in-flight slot `{ turnId, abort, start: { seq, messagesBefore } | null }`, the log; builds `TurnEngineDeps`, runs `runTurn` detached.
6. **Routes + SSE** — `apps/server/src/routes/chat.ts`, `apps/server/src/chat/sse.ts`; `app.ts`/`index.ts` wiring; body-parser failures → 400 in the error handler.
7. **One turn vocabulary** (added after the first wrap-up, decision 23) — browser-safe core entry `@gtd/core/turn` (`TURN_KINDS`/`TurnKind`, `VAULT_TOOL_NAMES`/`VaultToolName`, `QuickRepliesResult`, `TurnSink`/`TurnResult`/`TurnErrorPhase`/`TurnOutcome`); `@gtd/api` re-exports it instead of declaring copies; `buildTools` is pinned to it.

### Key Decisions
— session 2026-11-06
1. **Conceptual model, settled in the briefing (user questions).** The registry holds two kinds of state per user: `session` is a cache of the session file (loaded once per day, mutated and saved by the engine), `inFlight` + `log` are ephemeral. Persisted truth is the session file; after a restart the session is reloaded, the log is empty and an old cursor resyncs. Load balancing is out of scope by the plan's single-instance constraint (Task 12); multiple instances would need sticky sessions or a shared broker for the log plus a shared in-flight lock — recorded, not built. The "gate" in the briefing was `validateUserInput` (core's length cap + code-paste heuristic), named by its function from then on.
2. **The engine mutates the registry's own `Session` object.** `runTurn` receives `state.session`; `saveAtomically` appends in memory and serializes that same object, rolling back on a failed save. The registry adopts nothing after `turnEnd`; it only reads `session.messages.length`.
3. **`inFlight.start = { seq, messagesBefore }` instead of a registry-level `settledEntries` (user naming; plan deviation with identical semantics).** The number is a property of the running turn, known before Phase 1, and dies with the slot. 6.3's session load: turn in flight → `messages[0..messagesBefore)` and `cursor = start.seq − 1`; otherwise the whole session and `cursor = log.tip`. Deriving it (`messages.length − 1` while in flight) was rejected: Phase 1 may fail, an `await` sits between the Phase-2 save and `turnEnd`, and the opener (6.4) has no Phase 1.
4. **Two-stage slot (`start: null` during the session load).** The slot is claimed synchronously before the first `await` so a concurrent POST sees 409, and the in-flight check precedes the day check so the session is never swapped under a running turn. Rejected: a deduplicated load promise with a re-check after the await (more state for the same guarantee), placeholder numbers (`-1`).
5. **`resync` ends the stream.** AC-03 asks for "exactly one `resync` and nothing else"; the client reloads the session (6.3) and re-attaches with a fresh cursor. Keeping the stream open after a resync would leave a hole between the reloaded session and the live events.
6. **`seq` is seeded per user log when the log is created, from `Date.now()`.** Equivalent to the plan's "at boot" for the guarantee that a cursor from an earlier process is never servable; tests pass a fixed seed (1000) through `TurnRegistryDeps.seqSeed`.
7. **Unknown `GTD_PROVIDER` fails the boot** (`ConfigError`), unlike the CLI's silent fallback to anthropic; the provider's API-key variable joins the one "missing variables" message; `GTD_MODEL=""` counts as unset.
8. **Non-integer `cursor` → 400 `invalid_request`.** Only a syntactically valid cursor the log cannot serve gets `resync`; `?cursor=abc` is a client bug.
9. **Body-parser failures → 400 `invalid_request` by shape** (`asInvalidRequest`: a dotted `type` such as `entity.parse.failed` plus a 4xx `status`), generic message "Malformed request body". A router `URIError` (400, no `type`) still lands as 500 on purpose (Task 2 decision 13); the "revisit once bodies are parsed" note is resolved.
10. **An observer must never fail the turn.** The sink appends from the engine's stream loop, so `EventLog.append` catches a throwing listener and drops it, and the SSE writer ignores writes after the response ended or was destroyed (the `close` unsubscribe can race an event already in flight).
11. **`recover` for a rejected `runTurn`.** The engine reports every failure through `turnEnd`; a rejection is a contract violation. The registry still frees the slot (otherwise 409 forever), appends `error` + `turn-end` without `phase` and logs `chat.turn_crashed`. `phase` is optional on the wire for exactly this case.
12. **Wire details.** `data:` carries the whole event object including `type`, so `JSON.parse(data)` is a `SessionEvent`; `TurnFailedPayload extends ApiErrorPayload` narrows `code` to `"turn_failed"` (the `error` event has the HTTP error-body payload shape); `TOOL_NAMES` lives in `@gtd/api` as the closed set — the same six names as the web registry, which may alias it in 6.2; `@gtd/api` declares `TurnKind`/`TurnErrorPhase` itself (browser-safe rule, no core barrel import).
13. **Tool-row derivation** mirrors the CLI label and the web `AssistantToolMessage`: `file_path` for read/edit/write, `query`, `prefix` (empty string without one), candidates joined with `", "`; `summary` only for edit/write and only from a non-empty string; a name outside `TOOL_NAMES` (incl. `suggest_quick_replies`, which the engine filters anyway) produces no event; `toolError` emits `tool-end` so the row settles.
14. **One clock reading per turn.** `startedAt = now()` decides the day (`formatToday`) and is the engine's `now` for the whole turn, so a turn that crosses midnight belongs entirely to its start day: same session object, both saves into the same file, prompt date and tool gates consistent. The day switch happens only between turns (409 check first) and today only on `POST`. The user's follow-up (open app across midnight, opener under yesterday's conversation) became Task 16 (decision 19).
15. **Multi-device (user question).** `turn-start` carries the user's text so every client renders it from the stream; the POST answer is only 202. This is the command/event split: the client never distinguishes own from foreign messages. 6.2 must not render the message twice (wait for the event, or replace an optimistic copy by `turnId`). A device typing during another device's turn gets 409 and sees the running turn live.
16. **Dependencies by symlink, lockfile owed.** `pnpm install --offline` failed on the read-only store lock in the sandbox and the non-sandbox retry was denied by the auto-mode classifier. As in Task 3.2, the four packages are symlinked into `apps/server/node_modules` from `node_modules/.pnpm` (exact CLI versions, resolved and verified); `package.json` is correct, `pnpm-lock.yaml` must be regenerated with a normal `pnpm install` before the commit.
17. **`vault-file-version.ts` is a deliberate duplicate of the CLI closure** (12 lines). The improvements register already holds the `FileRepository.versionOf` idea for the time the Supabase repository exists; no core change for one more caller.
18. **`createApp` requires `turnRegistry`.** No optional "server without chat" configuration; the four route tests pass `stubTurnRegistry()` (in-memory fakes, never called).
19. **Plan amendment — Task 16 "Day rollover under an open app", deferred with trigger (user decision).** After the midnight discussion the user asked for a task at the plan end rather than half-solving it in 6.3/6.4: server day switch at every entry point + `resync` broadcast, client reset/banner/navigation/archive, and the open UX question (hard cut vs. finishing yesterday) to be decided on tester feedback.
