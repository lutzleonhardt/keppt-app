### Key Decisions
— session 2026-11-06

1. **Tracer bullet instead of layers (user decision).** 6.1 server turn + event stream (curl-visible) → 6.2 minimal `HttpChatService` (the app chats) → 6.3 session boot + re-attach → 6.4 opener on the server, empty-vault welcome, debug artifacts → 6.5 user-local day + daily turn cap. Every slice has a visible end-to-end check right after it lands. Rejected: the first proposal (6.1 core timezone, 6.2 server, 6.3 user-day, then 7, then 8) — correct in size, wrong in feedback order.
2. **Numbering: 6.1–6.5, Tasks 7 and 8 folded, 9–15 keep their numbers.** Renumbering would have broken references in task logs, memory and the plan's own cross-references (T9-AC IDs, "Task 10 JSONB", the deferral triggers of 14/15). The at-a-glance list carries the "7./8. folded" line so the gap is explained where someone looks for it.
3. **6.1 stays one slice (user: "kein Problem, wenn ein Commit etwas größer ist, wenn die Dinge zusammenbleiben").** ~20 files, about half tests, one goal: a turn runs detached and is observable. The evaluated split line — 6.1a registry + `POST /api/chat`, 6.1b event log + SSE — was rejected: 6.1a would run the engine into a stub sink that 6.1b replaces, and its only functional check would be reading the session JSON. The inner seams (log class, SSE writer, sink mapping) are unit-testable but have no reviewable outcome alone.
4. **Core timezone plumbing moves to the end (6.5); supersedes the "one change in Task 6" wording of Task-4 decision 3.** The dev path runs in the process zone like the CLI, so no slice before 6.5 needs the zone; `TZ=UTC` is a hosting property (Task 12). The plumbing shape is unchanged (`formatToday(d, timeZone?)` via `Intl.DateTimeFormat("en-CA")`, `BuildToolsOptions`, repository options, `TurnEngineDeps`), plus the one finding of this briefing: `buildSystemPrompt` derives weekday/month/day/year with local getters, so the zone must reach the prompt as well or prompt and gates disagree across midnight — `system-prompt.ts` and `request-builder.ts` joined the Key Locations.
5. **`FsTurnLogger` → core and `DEBUG=1` on the server ride with 6.4, not 6.1 and not their own slice.** The opener's live smoke needs the artifact (Task-5 decision 23 found the wasted model step only there); adding the ~6-file move to 6.1 would have pushed the biggest slice past ~25 files; a standalone mechanical slice would be ceremony for a 20-minute move. Rule recorded in memory: a mechanical move rides with the slice that first needs it.
6. **Vocabulary fixed in the blocks.** Event `kind` is the persisted turn kind `"user" | "opener"` (Task-5 decision 16; the Task-6 draft's `"auto-replan"` and Task 7's `"synthetic"` are gone). `turn-end` carries the engine `phase` on `outcome: "error"` (Task 5 asked the web side to render phases from one vocabulary). Error codes: `input_rejected` (400), `invalid_request` (400 — body-parser failures, non-string `message`, invalid `X-Timezone`; today such requests end as 500, which the error handler's "revisit once bodies are parsed" note anticipated), `turn_failed` (SSE `error` event, payload in the HTTP `ErrorBody` shape with the originating POST's `requestId`), `turn_limit_reached` (429, 6.5).
7. **`seq` is seeded at boot from `Date.now()`, and `resync` fires in both directions.** A counter from 1 could, after a restart, serve a stale cursor silently with events of the wrong process once the new log has grown past it; an epoch-seeded seq makes any pre-restart cursor older than the oldest retained event. A cursor beyond the tip (buggy client) also yields `resync` instead of waiting forever.
8. **The attach boundary is the turn, recorded in 6.1 and consumed in 6.3.** Lutz asked how session snapshot and stream replay avoid overlap. Two naive variants fail: "session as-is + cursor = tip" loses the in-flight turn's deltas (only in the log); "session as-is + replay from the in-flight `turn-start`" shows the phase-1 user message twice. Hence the registry records `startSeq` (seq of the in-flight turn's own `turn-start`) and `settledEntries` (session entry count at each `turnEnd`); the 6.3 snapshot returns `messages = entries[0..settledEntries)` and `cursor = startSeq − 1` (or the tip), read in one synchronous block. Replay and subscribe on attach also happen in one synchronous block — the sink appends synchronously from the engine's stream loop, so an `await` between them is the only way to lose an event.
9. **T7-AC-03 (legacy session files without origin markers) dropped.** There is no legacy reader since Task-5 amendment 4; the ID stays visible in the 6.3 block with the reason.
10. **6.2 attaches without a cursor as the interim; `status "error"` UI waits for 6.3.** Without the session endpoint the client opens the stream once at construction and lets the server replay the whole day log, which already restores the day after a page reload within one server run; after a server restart the chat starts blank until 6.3. The error *state* is tied to the re-attach probe (`/api/sessions/today` failing too), so it lands with the probe; 6.2 renders 400/409 and the SSE `error` event as catalog copy and returns to idle.
11. **Opener chain semantics (6.4).** `POST /api/chat/open` → 202 when due, else 204 — also 204 while a turn is in flight (the day has started) and on an empty vault. `POST /api/chat` runs the opener first when due, then the user turn, as one in-flight chain; the user turn runs regardless of the opener's outcome; a cancel during the opener lets the opener finish (not abortable) and the user turn then starts with an already-aborted signal and ends `aborted` with its phase-1 message persisted. Mirrors the CLI: `open` is the startup call, opener-before-user the rollover guard.
12. **User clarifications worth keeping (conceptual model, settled in the briefing):** (a) the cursor marks "from here the session has nothing", not "last turn"; two values exist — the snapshot cursor from the session load and the live cursor the client keeps from the last `id:` — and both go through the same `?cursor=` parameter, which the server does not distinguish; (b) SSE is push: `since(cursor)` runs once per connection, afterwards every append fans out to the open connections, the client never polls; (c) the client does not know afterwards which message came from the session and which from the stream — intended, that is XC-06; the 6.3 DTO must therefore deliver the same shape the event reducer produces; (d) older days (Task 14, deferred) are pure reconstructions from their session file and never touch the stream; a day change under an open app is 6.3's re-attach policy; (e) `EventSource` would resend `Last-Event-ID` by itself, but it cannot set headers, and Task 9's JWT must ride along — hence `fetch` + query parameter.
13. **Written at `/start-task` time without `/plan`.** The blocks follow the plan skill's schema (Instructions, Acceptance with stable IDs, Quick functional check, Key Locations, Key Discoveries); Key Locations were verified against the code read in this session; file counts in the amendment are estimates, not commitments.
14. **The 7/8 gap is closed in the skill, not by renumbering (user decision).** Lutz objected that `/start-task` reads `task-{N-1}-*.md`, so Task 9 would find no predecessor. Evidence: the rule is undefined for point tasks anyway, and the 3.1, 3.2 and 4 sessions each resolved "predecessor" as the heading before theirs in plan order. A full renumbering (6–10, 9–15 → 11–17) would have left ~20 references in the logs of Tasks 1, 2, 3, 5 and the beta-MVP cut pointing at the wrong tasks. The kit's `start-task` skill now defines the predecessor as the heading immediately before `## Task N` in `plan.md` (3.2 → 3.1, 4 → 3.2, 9 → 6.5), resolved from the heading list, never from `N-1` arithmetic; if the predecessor has no log yet, the nearest earlier heading with one. The 6 / 7 / 8 / 8.1 / 8.2 alternative was declined as churn. Plan numbering stays 6.1–6.5 with the "7./8. folded" line.
